# 用户识别功能链路（Intent Recognition）

> 抽象说明 FixLoop 中「理解用户想做什么」的端到端链路。  
> **实现边界与模块清单**以 `docs/superpowers/specs/2026-08-03-intent-router-design.md` 为准（含 §14–§18 后续增强：clarify-only、多轮指代、候选发现、LLM candidates、分层评测）。

---

## 1. 问题与边界

### 1.1 要解决什么

编码 Agent 的入口输入是开放自然语言（提问、粘贴堆栈、多句指令、含糊指代）。系统需要在**执行任何工具或改代码之前**回答：

1. 用户的主意图是什么（问、修、记偏好、重构、测试…）  
2. 是否存在多个可执行意图，以及它们的先后依赖  
3. 关键约束与对象是什么（文件、异常类型、范围）  
4. 当前是否足够自信可以自动执行；否则应澄清而非猜测执行  

### 1.2 明确不做

- 不替代下游 Agent Loop / Repair 流水线本身  
- 不做通用闲聊对话管理或开放域 NLU 平台  
- 首期不做并行工作流调度；多意图按依赖顺序串行  
- 不以「金集准确率 = 线上能力」作为唯一叙事  

### 1.3 在系统中的位置

```text
用户输入（REPL / 修复通道）
        │
        ▼
┌───────────────────────┐
│  用户识别（本链路）    │  → 结构化意图图 + 置信度 + 是否允许执行
└───────────────────────┘
        │
        ├─ 允许执行 → 按图串行调用既有能力（问答 / 记忆 / 修复提示 / …）
        └─ 需澄清   → 只提问，不触发副作用
```

识别层**只规划与门控**，不直接调度底层工具。

---

## 2. 能力全景

| 能力 | 说明 |
|------|------|
| 意图分类 | 闭集动作级意图（问答、解释、记忆、修复、审查、重构、实现、测试、排查、检索、计划、帮助、澄清、取消、越界等） |
| 多意图构图 | 单意图 / 多意图 / 单意图+约束 三种模式 |
| 槽位抽取 | 从堆栈与文本中提取可疑文件、异常类型等 |
| 置信融合 | 规则信号、语义相似、可选弱模型修正 |
| 澄清门控 | 低置信、无命中、歧义、冲突、指代失败 → 只澄清 |
| 多轮指代 | 依托会话历史消解「这个 / 刚才那个 / 修一下」 |
| 可观测 | 路由结果、澄清原因、指代结果、延迟与分层评测 |

## 3. 端到端链路（抽象）

```text
                    ┌─ 会话历史（说了什么）
用户话语 ──────────┤
                    └─ 意图投影（上轮意图摘要 / 待澄清状态）
                              │
                              ▼
                    ┌─────────────────┐
                    │ 1. 指代与续写   │  短句 → 可分类的完整表述
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ 2. 分段         │  多句 / 连接词 / 堆栈块
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ 3. 段级识别     │  规则优先 → 语义增强 → 弱时可选修正
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ 4. 意图规划     │  单 / 多 / 混合；建依赖与约束边
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ 5. 置信与门控   │  是否允许自动执行
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
           澄清回复      兼容主意图摘要    意图图交付执行器
```

### 3.1 指代与续写

- **历史优先**：以会话中用户说过的话为连续性来源。  
- **薄投影**：仅补充历史没有的结构（待澄清问题、上轮主意图与关键槽、近期对象引用）。  
- **典型改写**：「修一下」+ 上文堆栈 → 修复表述；澄清后的「修」+ 原句 → 合并后再识别。  
- **失败**：无法消解则进入澄清，而不是猜测执行。

### 3.2 分段

将一次输入拆成可独立判断的片段，并识别叙述顺序线索（然后 / 另外 / also…）。  
堆栈与代码粘贴尽量保持为完整块，避免被句号误切。

### 3.3 段级识别（分层）

1. **强规则层**：斜杠命令、记忆口令、显式「修」、堆栈形态、企业动作关键词等——确定性高、可解释。  
2. **语义层**：与动作原型的相似度，用于弱规则补强或冲突提示（环境无模型时可跳过）。  
3. **弱信号修正（可选）**：整图仍弱时，允许一次轻量结构化修正；非主路径。  

冲突策略示例：同句「修」与「重构」互斥 → 倾向澄清，而非静默选一边执行。

### 3.4 意图规划

| 模式 | 含义 | 交付形态 |
|------|------|----------|
| 单意图 | 一个可执行动作 | 单节点 |
| 多意图 | ≥2 个可独立执行的动作 | 带顺序/依赖的图 |
| 混合 | 一个可执行 + 若干约束 | 约束合并进主动作的槽位 |

约束示例：「只用改某文件」「先别跑全量测试」——附着到主意图，不单独执行。

### 3.5 置信与执行门控

门控输入包括：段级融合分、图级聚合分、是否歧义/冲突/无强命中。  

产品默认（交互通道）：

- **低于执行门槛 → 只澄清，不自动执行**  
- 帮助 / 取消等元意图除外  
- 修复专用通道可对「纯 issue」更激进地折叠为单一修复意图  

输出中显式携带：是否允许执行、澄清原因、候选意图（便于产品展示与观测）。

### 3.6 交付与执行

- **兼容摘要**：主意图、动作、槽位——方便旧链路只消费「一个意图」。  
- **权威结构**：意图图——多步时由薄执行器按拓扑串行调用既有能力。  
- 多数企业动作可先接「已识别」占位，再分期接通完整流水线。

## 4. 通道差异

| 通道 | 识别策略侧重 |
|------|----------------|
| 交互（REPL） | 允许多意图；低置信严格澄清；写入会话历史以支持指代 |
| 修复（issue） | 多段输入折叠为单一修复意图 + 约束；以堆栈与文件槽位为第一公民 |

同一套分类与构图能力，**策略与折叠规则按通道切换**。

## 5. 多轮状态（抽象模型）

```text
会话历史 ──────────────► 指代消解的「原文材料」
（用户说过什么）

意图投影 ──────────────► 指代/续作的「结构材料」
（待澄清、上轮意图、对象引用）
```

原则：

- 不另建平行「第二套聊天记录」替代会话历史  
- 投影随会话保存与重置；澄清悬空有有限生命周期  
- 识别路径也要保证用户话进入历史，否则多轮会断层

## 6. 质量与发现误路由

### 6.1 指标分层（企业视角）

| 层级 | 关注点 |
|------|--------|
| 正确性 | 主意图准确率、动作准确率、槽位命中 |
| 代价 | 严重混淆率（如「修复 ↔ 闲问」）、过自信错误 |
| 拒识 | 澄清精确率/召回、低置信仍执行率 |
| 多轮 | 指代消解成功率、澄清后续作成功率 |
| 校准 | 置信度与对错的一致性（如 ECE） |
| 体验 | 路由延迟分位；弱模型回退占比 |
| 分布 | 按场景分层（提问 / 堆栈修复 / 含糊 / 企业动作 / 压力集） |

### 6.2 评测集角色

- **回归金集**：防改坏；与规则同构时准确率可以很高——只作门禁。  
- **分布模拟集**：按近似真实流量加权的场景桶。  
- **Held-out 压力集**：故意不过拟合的难例；允许整体误路由率非零，用于诚实评估与面试叙事。  

推荐同时报告：

- 分布内误路由（门禁）  
- Held-out 误路由（压力）  
- 加权误路由（近似流量）  

### 6.3 如何发现误路由

1. **有标签**：金集回归、日志抽样人标、压力集。  
2. **无标签代理**：用户改口、取消、澄清后放弃、高置信却下游失败。  
3. **按代价优先**：严重混淆矩阵、过自信错误、本该澄清却执行。  
4. **闭环**：抽样 → 人标 → 入金集或压力集 → 只修可泛化的高代价洞（避免为单条 case 过拟合）。  

### 6.4 候选意图发现（补充 taxonomy 的输入）

系统**不自动**把新意图写入闭集，只产出可供评审的候选：

| 来源 | 含义 |
|------|------|
| 路由 Top-k / 澄清残留 / 冲突 | 识别时落败或互斥的意图信号 |
| 用户取消 / 改口 / 澄清选项 | 行为代理（高价值、需人标） |
| 离线 / 在线 LLM 提名 | 弱信号修正时**同一次**返回 `candidates[]`（闭集优先；新标签仅提名） |
| 金标差集（`--from-eval`） | 评测 case 预测≠金标 |

持久化为追加事件，再聚合成「意图卡」。人审通过后才进入闭集变更流程。

## 7. 设计原则（可对外口述）

1. **规则优先、语义增强、模型托底**——可解释、可回归、可降级。  
2. **图表达意图，串行执行**——先表达清楚「做什么、什么顺序」，调度保持简单。  
3. **低置信默认不执行**——用澄清换误动作，尤其避免误触发改码类能力。  
4. **历史承载连续性，投影承载结构**——多轮不另造平行对话库。  
5. **指标讲分层**——分布内门禁 ≠ 线上能力；压力集失败是预期信号。  

---

## 8. 演进方向（识别层）

优先级从高到低（产品视角）：

1. 真实流量抽样人标与周更误路由  
2. 澄清多轮状态机与槽位确认体验  
3. 企业动作从「识别占位」接到完整流水线  
4. 置信校准与按动作的代价权重  
5. （非目标）通用对话平台化、并行 DAG 产品化  

---

## 9. 一句话总结

用户识别链路把开放输入变成**可门控的意图图**：先消解指代与分段，再分层分类与构图，最后用置信度决定是澄清还是串行执行；质量上用**分布内回归 + 流量加权 + held-out 压力**三套尺子，而不是单一准确率。
