# FixLoop 上下文面试 MVP 开发计划

日期：2026-10-12。状态：P1（S1）已实现并完成相关测试；其余阶段待实施。S1 配置、调用与恢复边界见 `docs/S1_MODEL_BUDGET_ACCEPTANCE_2026-10-12.md`。

## 目标与已确认范围

完成一条可清楚解释的修复上下文主路径：可信输入接入 → 自然语言约束/决策提取 → owner 校验与版本化提交 → 当前节点投影 → 预算装配与历史压缩 → 模型调用 → 工具反馈 → 重试或恢复。

本版包含自然语言约束与决策的自动提取、校验和提交。明确项自动提交；歧义或冲突保留候选并给出原因，影响执行时阻断相关操作、请求澄清。用户无需逐条批准已明确表达的要求。

其余沿用讨论确认的面试 MVP 边界：以 Plan 驱动的 repair 主流程为保证范围，保留节点级决策，复用现有 EvidenceLedger、Observation、Plan journal、owner/generation、委派和恢复机制。没有演示面板、付费模型实验或发布级验证要求。

缓存由其他专项负责。本计划不修改 Provider 缓存策略、cache_control、prefix hash、摘要缓存 key/存储/失效策略或缓存指标。压缩结果的结构校验与缓存来源无关，缓存读取出的文本也经过同一个压缩结果校验器。实现前核对共享文件的已有差异，保留专项更新。

## 现状与真实差距

| 部分 | 已有能力 | 本版要补齐 |
| --- | --- | --- |
| 请求装配 | prepare_request 统一 XML/native 主循环；Plan 必需项保护、弹性配额、最终计量与 manifest | 明确一条支持路径，连入新提取结果与窗口配置 |
| 任务状态 | LongTaskState 保存原目标、显式 hard_constraints | 消息来源、约束版本/替代/撤销、增量提交入口 |
| 决策 | record_decision/replace_decision、revision、节点作用域、needs_review | 自然语言候选接入；用户消息依据与技术证据分别核验 |
| 证据 | 当前/历史用途、依赖校验、正文 freshness、最终消费记录 | 复用；不建设第二套证据图 |
| 委派/恢复 | 目标约束只读快照、来源核验、owner 重读、journal 对账 | 要求变化后失效旧任务结果；恢复提取进度及已提交版本 |
| 压缩 | L0–L5、近期保护、LLM 摘要与失败回退 | 全量/增量同一结构，按 token/完整条目缩减，完整交互回退 |
| 预算 | BudgetManager、子任务预留/结算、独立输入与输出上限 | 统一主循环/规划/子任务/提取/摘要口径，补辅助调用门禁 |

已有决策版本和证据消费能力分别见 DECISION_PROJECTION_ACCEPTANCE_2026-10-02.md、EVIDENCE_CONSUMPTION_ACCEPTANCE_2026-10-02.md。早期 LONG_TASK_CONTEXT 验收中关于“决策未实现”的说明已经被后续增量覆盖，不能据此重建相同功能。

## 关键契约

### 来源与自动提交

- 可信调用边界登记 source_message_id、run/task、来源种类、正文及 checksum；来源身份由运行时填写，模型不能声明自己代表用户。
- 原始用户输入与生成的 repair prompt 分开接入。不会把 L2 模板中的源码、日志、角色规则重新视作用户消息，也不重复提取同一个原始 Issue。
- 用户明确要求可以产生硬约束；用户明确选择可以产生用户决策。模型方案可以产生节点技术决策，不能创建用户硬约束或扩大工具权限。
- 提取输出包含种类、add/replace/revoke、原文位置/引用、目标记录、预期版本、作用域、理由和技术证据引用。模型置信分数不代替来源与提交校验。
- 用户决策通过独立 source_refs 核验原始消息；技术决策沿用 evidence_refs 核验代码/分析证据。不把用户消息伪装为源码 Observation 或已执行收据，不放宽已有技术决策的证据要求。
- 没有当前适用节点的用户选择先保存为有来源的候选，节点确定后再绑定并提交；不随意绑定第一个节点，也不增加通用任务级技术决策系统。
- 语义提取由模型完成。运行时校验原文锚点、来源身份、字段、范围、版本和证据；原文锚点存在不等于语义正确。互相矛盾且无法明确解析替代关系的条目进入 clarification_required，不使用 last-write-wins 自动裁决。

### 状态提交与恢复

- 约束记录具有 ID/revision/status/source_refs；替代/撤销保留历史。活动 hard_constraints 从最新版约束投影，避免多处维护可变真值。
- 决策复用已有节点级版本链，补来源类型和撤销语义；证据失效仍派生 needs_review，不自动确认旧结论。
- 提取批次绑定 source message、输入状态 revision、Plan version 和提取策略版本。owner 提交时比较预期版本；所有候选先校验，失败批次不发布部分活动状态。
- 在已有 journal 中保存提取 started/result/commit 状态、候选结果与消费进度。提交完成后才推进消息游标，重复消息或恢复不产生重复版本。
- 不额外承诺跨存储原子提交。提交未确认时依据持久记录对账；在结果未知的窗口禁止继续派发修改。
- 用户要求在执行期间变化，先由 owner 在安全边界接入。未停止或 uncertain 的副作用先完成现有对账；不以新约束覆盖未确认执行事实。

### 预算与调用

- 单次容量独立于累计消耗：输入上限取 prompt_budget、hard_cap、显式模型窗口减输出预留与余量的最小值。首版支持主用模型的显式配置，不猜测未知模型容量。
- 累计输入、累计输出、累计总 token 与调用次数分别记录。原 prompt_tokens 资源保持输入含义；添加明确的累计 total_tokens 限制，Explorer 不再向输入资源混记输出。
- 派发前同时预留调用次数与 token；正常返回按本次 usage 结算。没有 usage 或调用中断时保守保留预约，记录 estimated/actual/unknown；不会静默删除已发生但超限的消耗。
- 子任务在父账本预留 scope，子账本只限制内部执行；归并到父账本只结算一次。重试和辅助模型调用都消耗额度。
- 复用现有取消、期限和 Provider 适配，不重写 HTTP 客户端或 Provider 内部重试。一次运行时预约覆盖 Provider 内部重试的逻辑调用，物理请求次数未暴露时不声称精确计数。
- 模型调用目的标记为 repair/planning/exploration/extraction/summary，便于解释预算构成。

### 压缩

- 全量/增量使用相同 schema：confirmed_facts、hypotheses、rejected_hypotheses、files_changed、verification、next_action、evidence_refs；事实与假设保持区别，结构校验不证明事实正确。
- 摘要输入在有界预算内按完整交互/记录选择，保留证据引用、关键失败信息和省略说明；不再先对每条任意取少量字符后假装覆盖全部旧历史。
- 摘要输出按 token 与完整字段/条目裁减，最终重新序列化合法结构；删除 300 字符硬切输出的行为。
- 新摘要合并旧摘要后只保留一个有效摘要块；避免新旧摘要并存形成重复或冲突。
- 摘要失败、超时或额度不足时采用确定性回退：权威 state 独立完整保留，近期交互按完整工具调用/结果组保留；装不下则有原因地舍弃可选内容，仍不足时明确阻断。
- 摘要仅作历史辅助，不写回原始证据、硬约束、活动决策或执行收据。

## 阶段 P1：统一模型预算边界与主用窗口配置

目标：让后续新增的提取和摘要调用从接入之初就受同一任务预算、取消与期限管理。

模块：agent_runtime/budget_manager.py、policy.py、config.py；新增小型 model_call_budget.py；接入 loop_protocols.py、runtime.complete_once、src/repair/plan_binding.py、src/collaboration/exploration_runtime.py、src/agents/explorer.py。Intent 前置调用若属于同一次 repair，也接入同一调用目的/账本，避免只覆盖主循环。

实现：先定义预约/结算/未知用量接口，再迁移选定 repair 路径。保留已有客户端与协议封装，把现有重复扣费点替换成统一接线。模型窗口采用显式配置；必需内容超过容量时仍阻断。

验收：

- 主循环、规划、子任务与辅助调用使用同一累计口径；父子预留不双计。
- 额度不足时零派发；取消和超时保守计账；恢复不退还未知消耗。
- Provider 实际消耗超预约时如实记录，阻止后续调用，账本不拒记。
- 输入加输出预留超过模型窗口时被校验或缩减可选输入。

预计生产代码新增/修改 350–550 行，测试 180–280 行。相关测试：test_llm_budget.py、test_runtime_policy.py、test_exploration_runtime.py，以及新增本次调用预约/结算行为测试。

## 阶段 P2：消息来源与版本化约束/决策提交

目标：建立提取候选可提交、可撤销、可恢复的最小状态契约。

模块：agent_runtime/plan_runtime/long_task.py、session.py、decisions.py、src/state.py；新增 task_messages.py、constraint_records.py；按需调整 checkpoint 与委派消费引用。

实现：复用 journal 存储来源消息和提取批次；建立来源引用校验、约束版本链和活动投影；扩展已有决策记录以区分用户消息来源与模型技术证据；owner 接口提交完整候选批次。原始目标全文继续保留。

验收：

- 来源正文/身份被修改、跨任务引用、错误 revision、越权来源均拒绝提交。
- 新增/替代/撤销约束和决策保留历史，当前投影仅包含活动版本。
- 同消息重复处理不重复写版本；提交窗口中断后可对账。
- 已确认 patch/test 收据不因约束或决策版本变化而被误当成未执行操作。

预计生产代码 350–550 行，测试 180–260 行。相关测试：test_long_task_context.py、test_decision_projection.py、test_required_long_task_context.py；新增来源和约束版本行为测试。

## 阶段 P3：自然语言增量提取与自动提交接入

目标：自动消费用户要求和模型明确形成的节点方案，把通过核验的约束/决策写入权威状态。

模块：新增 agent_runtime/task_extraction.py 及有界结构化 prompt/schema；接入 src/repair/plan_binding.py、agent_runtime/agent_loop.py 或其明确任务更新服务。由 L2 决定接入时机，L1 提取/提交服务不 import src。

触发时机：

1. 原始用户 Issue 登记后、模型规划前，提取任务约束和用户明确选择。首个 Plan 创建后提交可绑定的节点决策。
2. 受信任的新用户消息进入同一任务时，先增量提取并提交，再装配下一轮请求或派发新委派；提供 owner 消息入口，不增加聊天 UI。
3. 主模型明确形成节点方案后，在工具修改派发前提取技术决策，关联当前已核验输入。普通探索性假设保留候选身份。
4. 对每个新的可信来源批次最多一次提取和一次有预算的结构修复；长输入按有界片段完整覆盖并记录游标，未处理完成前不派发受影响写入。没有新来源时不调用提取模型。

提取调用只返回候选，不带工具权限。检查重复、替代/撤销对象、原文锚点、节点范围与证据后由 owner 自动提交。待澄清内容返回稳定原因与问题；调用失败不默默跳过要求继续写入。对生成的模板、源码、日志、子任务回复不会自动赋予用户来源身份。

验收：

- 中文/英文多条要求、否定、例外、明确替代与撤销都进入正确候选/版本路径。
- 用户选择与模型技术决策采用不同依据；没有代码证据的猜测不会成为已确认技术决策。
- JSON 畸形、输出截断、伪造来源/证据、冲突、预算不足不会发布部分活动约束。
- 用户补充约束后，下一轮 state 与新委派消费新版；旧委派结果按现有 freshness 契约失效。
- 重试/恢复只处理未提交来源，不从摘要重建用户约束。

预计生产代码 400–650 行，测试 200–320 行。新增 test_task_extraction.py；补入主循环、Plan binding、子任务一致性和恢复的相关行为测试。

## 阶段 P4：统一历史压缩结构与有界回退

目标：修正 L5 全量/增量格式差异、任意字符切断和回退工具组不完整的问题。

模块：agent_runtime/compression_pipeline.py、context_manager.py；必要时新增 history_summary.py，把格式校验和完整交互选择从管线控制代码拆出。

实现：保留 L0–L5 总体机制与已有近期保护，统一摘要 schema、输入装箱、输出 token 限额和合并行为；make_summarizer 接入 P1 辅助调用接口；按同一结构校验所有来源的摘要文本，不改摘要缓存 key 或磁盘实现。

验收：

- 首次与增量摘要始终可解析；新摘要替代旧摘要，证据引用仍可追溯。
- 全量与增量均保留事实/假设区分、关键失败及遗漏说明。
- 异常/超时/额度耗尽时保留受保护 state 与完整近期交互；native call/result 不被拆开。
- 压缩不能更新活动约束/决策，也不能改变 canonical 历史与原始 Observation。
- 缓存返回不符合新摘要结构的文本时，由压缩结果校验给出不可用原因并走回退；不修改缓存记录、键或命中指标。

预计生产代码 200–350 行，测试 120–200 行。相关测试：test_compression_pipeline.py、test_context_manager.py、test_summarization_taskstate.py、test_tail_protect.py、test_required_long_task_context.py。

## 阶段 P5：主路径集成与面试说明收敛

目标：把预算、提取、状态、压缩、委派与恢复接成同一条可说明的路径，形成明确支持边界。

模块：src/repair/plan_binding.py、agent_runtime/context_manager.py、checkpoint.py 及新服务接线；补短版设计说明和面试问答，不增加演示产品。

完成条件：

- 原始 Issue 自动提取 → Plan → 主模型方案决策 → 读改测 → 失败反馈 → 下一轮上下文顺序明确。
- 新约束或撤销接入后，当前 state/委派范围/活动决策一致；旧结果不回流。
- 压缩压力与重启后，活动约束和决策版本由 journal 重建，已确认副作用不重放。
- XML/native 选定 repair 路径均消费最终装配请求；manifest 记录状态/决策版本和实际选中证据，模型理解程度不由 manifest 推断。
- 主用配置明确输入窗口、输出预留、累计预算和必需项超限行为。
- 文档明确普通 L1、外围独立入口和选定 repair 主路径的覆盖区别。

预计生产接线 100–200 行，集成测试 120–200 行；设计/面试文档约 100–160 行。形成三个口述案例：压缩后保留任务；补丁后旧输入失效但成功操作不重放；用户更新要求后子任务旧结果失效。

## 顺序、验证与协作边界

执行顺序：P1 → P2 → P3 → P4 → P5。P3 的模型提取依赖 P1 预算与 P2 提交契约；P4 依赖 P1；最后统一检查真实调用接线。

预计生产代码新增/修改约 1400–2300 行，测试约 800–1260 行，另有短文档；为审查量级估算，不是必须达到的行数。优先复用已有服务，不新增 LLM 框架、证据数据库、泛化事件平台或第二套 Plan 运行时。

每阶段使用独立分支/PR 单元，沿用 CLAUDE.md 的 M{m}/D{d}/{task-slug} 规范；阶段名不是新的里程碑编号。实施前核对当前分支与未提交差异，以已确认归属安排隔离，保留其他专项工作。远端推送需单独授权，合并走 PR。

每阶段运行新行为与直接相关测试；失败修复后按 nodeid 精确复验，已通过且未受影响的结果继续有效。修改文件执行 Ruff check/format check 和 diff whitespace 检查。P5 仅补跨模块关键路径，避免重复整批测试。没有显式授权不运行全量测试或付费模型调用；不把受控模型测试描述为语义提取准确率或在线修复率提升。

本计划的完成标准是机制、接线和失败契约完整，面试中能追溯到明确模块并解释技术取舍。缓存优化、自动经验学习、通用语义冲突裁决、全部入口迁移和演示面板继续由已确认范围排除。
